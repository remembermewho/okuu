# Окуу

Сервис учёта оплат для учебных центров, курсов и секций (языки, подготовка к ОРТ, спорт, танцы, музыка,
робототехника). Оплата ручная: бот присылает родителю напоминание с реквизитами центра, родитель платит и
отправляет чек, администратор отмечает оплату — родитель получает подтверждение. ТЗ — [docs/TZ.md](docs/TZ.md), правила работы с кодом — [CLAUDE.md](CLAUDE.md).

## Запуск для разработки

Нужны Docker Desktop (запущенный), Go 1.23+ и Node 20+. Одна команда в корне репозитория:

```sh
make dev       # или, без make (PowerShell на Windows): npm run dev
```

Поднимает PostgreSQL в Docker и ждёт его готовности, затем параллельно запускает:

| Что | Адрес |
| --- | --- |
| Приложение (Vite) | http://localhost:5173 |
| Лендинг | http://localhost:5180 |
| API | http://localhost:8080 (приложение ходит в него через прокси `/api`) |

Логи всех трёх — в одном окне с префиксами `[api]`, `[app]`, `[landing]`. **Ctrl+C** останавливает всё; если
один процесс упал, остальные тоже останавливаются (чтобы не работать с полуживым стендом). Если `.env` нет — он
создаётся из `.env.example`; если нет `frontend/node_modules` — один раз выполняется `npm ci`. Регистрация локально
свободная (`REGISTRATION_MODE` пуст → `open`). Порты меняются через окружение: `HTTP_ADDR`, `APP_ORIGIN`,
`VITE_PORT`, `VITE_API_TARGET`, `LANDING_PORT` (скрипт — [scripts/dev.mjs](scripts/dev.mjs)).

## Локальный запуск по частям

```sh
cp .env.example .env   # и заполнить ENCRYPTION_KEY
make db                # PostgreSQL 16 в Docker (порт 5433)
make migrate           # миграции (сервер применяет их и сам при старте)
make run               # API на http://localhost:8080
```

Фронтенд (Node 20+), во втором терминале:

```sh
cd frontend
npm ci
npm run dev            # http://localhost:5173, /api и /webhooks проксируются на :8080
```

Проверки фронтенда: `npm run typecheck`, `npm run lint`, `npm test`, `npm run build` (сборка — в `frontend/dist`).
Клиент API генерируется из `docs/openapi.yaml`: после правки спецификации — `npm run gen:api` (файл
`src/api/schema.d.ts` коммитится). E2E на настоящем бэкенде: `npm run e2e:install` (один раз — Chromium), затем
`npm run e2e` — сам создаёт чистую базу `okuu_e2e` в контейнере из `make db`, поднимает API на :8091 и фронтенд
на :5174 (dev-сервер на :8080/:5173 не трогает); отчёт со скриншотами 390 и 1280px — `npx playwright show-report`.
Без контейнера `okuu-db` (так в CI) — `E2E_PG_URL=postgres://user:pass@host:port npm run e2e` и клиент `psql` на машине.
В CI e2e — отдельная задача; при падении отчёт Playwright лежит в артефакте `playwright-report` прогона.

Тесты: `make test` — с интеграционными на PostgreSQL из `make db`; `make test-short` — только юнит-тесты.
Код запросов: `make sqlc` (sqlc в Docker, сгенерированный код коммитится).
Ручная проверка API: [requests/](requests/) — файлы для расширения VS Code REST Client.
Спецификация API для фронтенда — [docs/openapi.yaml](docs/openapi.yaml) (OpenAPI 3.1; тест сверяет её с роутером
и проверяет по ней реальные ответы), коды ошибок — [docs/errors.md](docs/errors.md).

## Ручная проверка Telegram-бота на dev

Нужен свой тестовый бот (не боевой): создайте его у [@BotFather](https://t.me/BotFather) и пропишите в `.env`
`TELEGRAM_BOT_TOKEN` и `TELEGRAM_BOT_USERNAME` (без `@`). Токен никому не показывайте и не коммитьте.
В dev бот работает через long polling — публичный адрес и вебхук не нужны. Один токен — один запущенный
сервер: второй процесс с тем же токеном получит от Telegram 409 Conflict.

1. **Запустить сервер:** `make db`, затем `make run`. В логе должно быть `telegram: бот запущен (polling)`.
2. **Владелец:** `requests/auth.http` → register (или войдите существующим).
3. **Родитель со своим номером:** в `requests/telegram.http` впишите в `@myPhone` номер своего Telegram-аккаунта
   и выполните запросы 1–2 — появится ученик «Тестов Бот» с родителем на ваш номер (`parent.tg_status = none`).
4. **Приглашение:** запрос 3 — в ответе `bot_url` (`https://t.me/<бот>?start=…`), тексты для WhatsApp
   на русском и кыргызском и `whatsapp_url`.
5. **Привязка в Telegram** (с телефона, на котором ваш номер):
   откройте `bot_url` → «Запустить» → бот покажет центр, детей и текст согласия → «Согласен» →
   «📱 Поделиться номером» → «Готово! Вы подключены к центру…».
   Запрос 4 в `telegram.http` — у родителя `tg_status = active`; в журнале (`audit?action=parent.`) —
   `parent.telegram_link` с `consent_at`.
6. **Команды и меню:** после привязки внизу чата — постоянная клавиатура «💰 Баланс · 💳 Как оплатить · 📅 Посещения ·
   ❓ Помощь»; команды — в кнопке «Меню» у поля ввода (`setMyCommands` при старте). `/balance` — баланс и
   абонемент, «💳 Как оплатить» — реквизиты и инструкция центра из «Настроек» (по блоку на каждый центр; пусто —
   «уточните у администратора»), `/attendance` — посещения за месяц; если детей несколько — сначала выбор ребёнка,
   в ответах кнопка «« Меню». Старые кнопки «Оплатить» из прежних сообщений и `/pay` отвечают «Как оплатить». `/stop` —
   уведомления отключены (`tg_status = stopped`); `/start` — снова включены. Непонятный текст — подсказка и меню.
   Язык: по умолчанию бот только русский (`BOT_LANGUAGES=ru`, команды `/lang` нет); `BOT_LANGUAGES=ru,ky`
   включает выбор языка `/lang` (кыргызские тексты сначала проверить носителем языка).
7. **Напоминания и оплата** — `requests/reminders.http`: запись в группу с начислением → «Напомнить»
   (сообщение с суммой и блоком «Как оплатить:» — реквизиты из «Настроек» как есть, кнопка только «Баланс
   и посещения»). Родитель платит сам и отправляет чек администратору; «Отметить оплату»
   (`/students/{id}/payments`) — в Telegram сразу «спасибо, оплата получена» (9:00–20:00 по Бишкеку; ночью — утром).
8. **Чужой номер:** пригласите родителя с другим телефоном и поделитесь своим — бот вежливо откажет,
   приглашение останется действительным.

Что не проверить вручную на dev: блокировку бота (403 → `tg_status = blocked`) и лимиты Telegram удобнее
смотреть в тестах (`backend/internal/httpapi/telegram_test.go`, `backend/internal/telegram`) — там фейковый Telegram.

## Лендинг

Главная страница сервиса — статический HTML и CSS без фреймворков и без JS, в [landing/](landing/):

- `landing/src/index.html` — все тексты главной; `offer.html` и `privacy.html` — **черновики** оферты и политики
  персональных данных (сверху плашка «Черновик — требует проверки юристом», для поисковиков — `noindex`);
- `landing/config.json` — название, слоган, описание для поисковиков, контакты (`whatsapp`, `telegram`, `email`)
  и реквизиты. В HTML они стоят как `{{ключ}}`. Значения в `[скобках]` — заглушки: сборка напоминает, что их пора
  заполнить. Адреса `siteUrl` и `appUrl` там локальные (для разработки); в проде их заменяют `SITE_URL` и
  `APP_URL` при сборке (`node landing/build.mjs --prod` не соберёт с `http://` или `localhost`);
- `landing/img` — скриншоты демо-центра и картинка для соцсетей, `landing/fonts` — Golos Text (лицензия OFL).

Посмотреть локально (нужен только Node 20+, `npm install` не нужен):

```sh
node landing/build.mjs --serve        # собрать в landing/dist и открыть http://localhost:5180
```

Ссылки «Попробовать бесплатно» и «Войти» ведут на `appUrl` (локально — `http://localhost:5173`).
Переснять скриншоты после изменений в приложении — `cd frontend && npm run screenshots` (демо-центр в отдельной
базе `okuu_screens`, свой API на :8091; нужен контейнер из `make db`): картинки обновятся в `landing/img`.

Выложить: заполнить заглушки в `landing/config.json` и задать `LANDING_DOMAIN` в `deploy/.env`. Лендинг
собирается в образе `caddy` (`deploy/caddy.Dockerfile`) с `SITE_URL=https://<LANDING_DOMAIN>` и
`APP_URL=https://<APP_DOMAIN>`; Caddy отдаёт его на `LANDING_DOMAIN`, приложение — на `APP_DOMAIN`.

## Деплой на VPS

**Пошагово — [docs/DEPLOY.md](docs/DEPLOY.md)**: сервер, deploy key и `git clone`, `deploy/.env`, первый запуск,
миграции, суперадмин, демо, вебхук бота, проверка HTTPS, бэкапы, обновление и откат.

Кратко: один сервер и Docker Compose ([deploy/docker-compose.prod.yml](deploy/docker-compose.prod.yml), проект
`okuu-prod`): `caddy` (HTTPS, статика приложения и лендинга, собранные в его образе) → `app` (API, вебхуки,
фоновые задачи, миграции при старте) → `postgres` (том `pgdata`). Наружу — только 80 и 443 у `caddy`; у `app`
и `postgres` портов нет (Docker публикует порты в обход ufw). Секреты — только в `deploy/.env` на сервере
(образец — [deploy/.env.prod.example](deploy/.env.prod.example)). Бэкап — `deploy/backup.sh` по cron
([deploy/okuu-backup.cron](deploy/okuu-backup.cron)), 14 дней; восстановление — `deploy/restore.sh`.
CI ([.github/workflows/ci.yml](.github/workflows/ci.yml)) проверяет код и собирает образ; сам деплой ручной.

В командах ниже `docker compose -f deploy/docker-compose.prod.yml` — то же, что `dc` в docs/DEPLOY.md.

Healthcheck контейнера `app` — `GET /readyz` (БД, миграции, планировщик); наружу `/healthz` и `/readyz` Caddy
не отдаёт. Логи app — JSON, по строке на запрос: `request_id`, метод, шаблон маршрута (без токенов и телефонов),
статус, длительность; тот же `request_id` — в заголовке `X-Request-ID` ответа.

При остановке сервер дожидается текущих запросов и фоновых задач (до 20 с) — начисления и рассылки
не обрываются на середине. Миграции назад сами не откатываются: делайте их обратно совместимыми.

### Сброс пароля (поддержка)

Сотруднику, который работает только в одном центре, пароль сбрасывает владелец: «Сотрудники → ⋮ → Сбросить
пароль» — одноразовая ссылка на 24 часа. Владельцу центра и сотруднику, который работает в нескольких центрах,
ссылку выдаёт поддержка — после того как убедилась, что это он (звонок с его номера, знакомый голос и т. п.):

```sh
cd /opt/okuu
docker compose -f deploy/docker-compose.prod.yml exec app /server user reset-link --phone=0700123456
# Ссылка для смены пароля (Айгуль Асанова), действует до 22.10.2026 15:04:
# https://<домен>/reset/<токен>
```

Локально — `cd backend && go run ./cmd/server user reset-link --phone=0700123456`. Ссылку передайте человеку
лично (в мессенджер на его номер). Она работает один раз; прежние неиспользованные ссылки этого человека
перестают работать; после смены пароля все его сессии закрываются. В журнал его центров пишется
`user.password_reset_issue` и `user.password_reset_done` (без паролей и токенов).

### Подключение центров и панель суперадмина

Регистрация центров — `REGISTRATION_MODE` в `deploy/.env`:

| Режим | Как регистрируются | По умолчанию |
| --- | --- | --- |
| `invite` | только по одноразовой ссылке `{APP_ORIGIN}/register/<токен>` (14 дней); без неё — «Регистрация по приглашению» и кнопка WhatsApp на `SUPPORT_WHATSAPP` | prod |
| `approval` | кто угодно, но центр — заявка (`pending`): владелец видит «Заявка на рассмотрении», пока вы не одобрите | — |
| `open` | свободно (в prod — только если задать явно) | локально |

По ссылке центр сразу активен в любом режиме. Кнопки на лендинге — `registration` в `landing/config.json`
(`invite` — «Оставить заявку» в WhatsApp, `open` — «Попробовать бесплатно»); держите его как `REGISTRATION_MODE`.

**Первый запуск (режим `invite`):** суперадмина ещё нет — первую ссылку выдаёт консоль, по ней вы регистрируете
свой центр (или используете владельца демо), затем выдаёте себе права:

```sh
docker compose -f deploy/docker-compose.prod.yml exec app /server admin registration-link --note="мой центр"
# … зарегистрироваться по ссылке …
docker compose -f deploy/docker-compose.prod.yml exec app /server admin grant --phone=0700123456
# снять права — admin revoke --phone=…
```

Через API права суперадмина не выдаются никак. После входа в меню аккаунта (и в «Ещё» на телефоне) появится
«Панель платформы» (`/admin`):

- **Центры** — поиск по названию, имени и телефону владельца, фильтр по статусу; заявки сверху; тариф,
  «оплачено до» (прошедшая дата подсвечена «просрочено» — центр **не** блокируется сам), учеников, последний вход.
- **Карточка центра** — «Одобрить заявку», «Приостановить доступ» (с причиной; владелец видит «Доступ приостановлен,
  свяжитесь с поддержкой», бот и напоминания центра останавливаются, данные сохраняются), «Вернуть доступ», тариф
  и «оплачено до», «Ссылка сброса пароля владельца» (заменяет `server user reset-link`; команда остаётся для аварий),
  журнал платформы по центру.
- **Ссылки регистрации** — создать (с пометкой, для кого), скопировать или отправить в WhatsApp (ссылка видна
  один раз), отозвать неиспользованную; у использованной — центр, который по ней зарегистрировался.

Учеников, родителей, операции и журналы центров панель не показывает — только количество. Все действия
суперадмина и консольных команд — в отдельном журнале `platform_audit_log`.

### Демо для показа

Демо-центр «Демо: учебный центр «Пример»» — чтобы показать сервис клиенту без его данных: 40 вымышленных
учеников в 4 группах (3 тарифа, 2 преподавателя и администратор), история оплат за три прошлых месяца разными
способами, 3 отменённые оплаты, 8 должников с разной просрочкой, 5 «ожидают оплаты», 2 ушедших, посещаемость
за две недели (сегодня не отмечено) и журнал. Телефоны — только тестовые `+996 555 0XX XXX`.

```sh
# на сервере
docker compose -f deploy/docker-compose.prod.yml exec app /server demo seed --phone=0555099001 --password='<пароль>'
# локально
cd backend && go run ./cmd/server demo seed --phone=0555099001 --password='<пароль>'
```

Вход — этим телефоном и паролем (владелец). Сотрудники демо с тем же паролем — чтобы показать другие роли:
`0555090001` и `0555090002` — преподаватели, `0555090003` — администратор.
После показа (или перед следующим) — `server demo reset`: демо-центр пересоздаётся с нуля с тем же владельцем
и паролем, даты истории — от сегодняшнего дня. Повторный `demo seed` делает то же, но с новым телефоном и паролем.

- Удаляются и пересоздаются только центры с флагом `is_demo`; настоящие центры и их пользователи не трогаются.
  Телефон, который уже работает в настоящем центре, для демо не принимается (его пароль не меняем).
- В демо-центре не работают Telegram и напоминания: бот его не видит, автонапоминания и уведомления
  («оплата получена», «не был») не отправляются, «Напомнить» и «Пригласить в Telegram» отвечают `demo_center`.
- Остальное работает как обычно: можно принять оплату, отметить занятие, добавить ученика — до следующего `reset`.
- Пароль в командной строке остаётся в истории оболочки: для демо задайте отдельный пароль.

### Онлайн-оплата (выключена до Finik)

Сейчас оплата ручная: владелец пишет в «Настройках» реквизиты и инструкцию, бот присылает их в напоминании
о долге и по кнопке «💳 Как оплатить», родитель платит и отправляет чек администратору, тот нажимает «Отметить
оплату» — родителю приходит «Оплата получена». С `ONLINE_PAYMENTS_ENABLED=false` (по умолчанию):

- ссылки оплаты не создаются; `GET/POST /api/v1/pay/{токен}` отвечают `404`, как на неизвестную ссылку,
  а страница `/pay/:token` пишет «Онлайн-оплата не подключена, уточните способ оплаты у администратора»;
- задача `payments.reconcile` не запускается, `/webhooks/finik` не регистрируется;
- в интерфейсе нет ничего про онлайн-оплату (строка Finik в настройках, «Онлайн (Finik)» в отчёте — только если
  такие оплаты уже были). Флаг фронтенд берёт из `GET /api/v1/config`.

Код, таблицы (`payment_links`) и тесты онлайн-оплаты на месте (тесты гоняются с включённой оплатой). Включить
вместе с Finik, когда провайдер будет реализован: в `deploy/.env`

```env
ONLINE_PAYMENTS_ENABLED=true
FINIK_ENABLED=true
FINIK_API_KEY=<ключ от Finik>
```

и `docker compose -f deploy/docker-compose.prod.yml up -d app`. `FINIK_ENABLED=true` без `ONLINE_PAYMENTS_ENABLED=true`
сервер не запустит (ошибка конфигурации). Кнопку «Оплатить» в боте (ссылка на долг ребёнка) тогда нужно вернуть
отдельно — сейчас бот ссылок не выдаёт.
